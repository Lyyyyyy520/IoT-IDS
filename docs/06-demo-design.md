## 1. 概述

本项目的最终交付是**一个可现场演示的智慧社区 IoT 僵尸网络入侵检测系统**。本文档定义现场演示的完整方案：如何用低成本物理器件搭建一个"数字孪生智慧社区"沙盘，把树莓派升级成"社区安全机器人"，现场演示"僵尸网络入侵 → 传播 → GNN 检测 → 自动隔离"的完整攻防闭环。

**核心叙事（一句话）**：

> 我们部署了一个"社区安全机器人"（树莓派），它用**设备图神经网络**实时守护智慧社区，通过**数字孪生**看清每台设备的状态，用**语音**播报攻击并**自动隔离**受感染的设备。

## 3. 数据集与模型的角色

**数据集只用来「训练模型」，现场演示跑的是「训练出来的那个模型」。**

```
┌─────────────────────────────────────────────────────────────────┐
│  阶段一：训练（离线，用数据集）                                    │
│  CICIoT2023 数据集（含 IP + 标签）                                │
│       ↓ 建设备图（节点 = 设备，边 = 通信）                         │
│  设备图 GNN 训练 → 学会识别「被感染设备的流量模式」                 │
│       ↓ 导出                                                      │
│  best_model.onnx（模型文件，最终产物）                            │
└─────────────────────────────────────────────────────────────────┘
                              ↓ 同一个模型
┌─────────────────────────────────────────────────────────────────┐
│  阶段二：演示（在线，物理设备现场）                                │
│  树莓派 + ESP32 设备群（摄像头/门禁/路灯/传感器…）                 │
│       ↓ 实时抓包（backend/services/traffic_capture.py）          │
│  提取流量特征 → 建设备图（节点 = 现场设备，边 = 现场通信）          │
│       ↓ 加载 best_model.onnx 推理                                 │
│  输出：每台设备的实时风险等级（🟢绿/🟡黄/🟠橙/🔴红）               │
│       ↓ 触发分级响应 + 语音播报 + 实体反馈                         │
│  三端显示：哪台设备被僵尸网络感染                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.1 模型必须能「泛化」

现场设备的 IP 和数据集里的 IP 不一样（数据集 `192.168.137.x`，现场 `192.168.4.x`）。因此：

- ✅ **对**：节点特征 = 流量统计（包数、字节数、端口多样性、协议分布…）；IP 只用来"画图"（定义边），不作为模型特征
- ❌ **错**：把 IP 地址本身当成特征喂给模型 → 现场换 IP 就失效

### 3.2 四级风险分类（贴合分级响应 L1/L2/L3）

设备图 GNN 做**四级风险分类**，直接映射项目已有的分级响应与风险色：

| 级别 | 设备状态 | 风险色 | 含义 | 响应 |
|------|---------|--------|------|------|
| 0 | 正常 Benign | 🟢 绿 | 设备行为正常 | 无 |
| 1 | 侦察 Recon | 🟡 黄 | 设备在扫描/踩点 | L1 观察记录 |
| 2 | 拒绝服务 DoS/DDoS | 🟠 橙 | 设备在发动洪水攻击 | L2 告警 |
| 3 | 僵尸网络 Botnet | 🔴 红 | 设备已被 Mirai 感染控制 | L3 隔离 |

**标签规则 = 取最大严重度**：一个设备有多种行为时，取最严重的行为作为标签。

> 语义要点：僵尸网络（Botnet）是**设备的感染状态**，DDoS/DoS/Recon 是**攻击行为**。两者是不同层次——僵尸网络意味着设备"已被控制"，是最高风险，必须隔离。

### 3.3 解决「正常流量稀缺」问题

CICIoT2023 的良性流量天生稀缺（只覆盖 75 台设备，占全量 32%）。采用**时间切片**方案：

- 节点不定义为"设备"，而定义为"设备 × 时间窗口"的快照
- 良性时段（约 28 小时）切成时间窗口 → 正常节点从个位数扩充到数百个
- 配合类别权重 / Focal Loss 处理残余不平衡

## 8. 设备针对性反应 + 分级阻断（震撼性核心）

**每种设备被入侵后有"专属后果"**，用设备自己的执行器实现，而非统一"亮红灯"。每个反应都用设备自己的执行器（舵机¥5、继电器¥5、LED¥1、蜂鸣¥2），ESP32 原生支持，成本几乎为零。

### 8.1 每台设备的行为剧本（正常 → 被入侵 → 阻断）

| 设备 | 正常行为 | 被入侵后的现场行为 | 阻断后的反应 | 危害叙事 |
|------|---------|-------------------|-------------|---------|
| 📷 智能摄像头 | 云台缓慢扫描，5s 心跳上报 | **云台疯狂乱转**，大屏显示"画面被劫持"（雪花+HACKED） | 云台停止 → 摄像头断电 → LED 变红 | 隐私泄露 |
| 🚪 智能门禁 | 门锁关闭，上报"关门" | **舵机转动，门锁"自己打开"**，反复开合 | 舵机强制锁死 → LED 变红 | 物理安全失守 |
| 💡 智能路灯 | 上报光照值，天暗亮灯 | **灯光疯狂闪烁 / 熄灭** | 灯光稳定/熄灭 → LED 变红 | 社区陷入黑暗 |
| 🔌 智能插座 | 上报功率，控制通断 | **继电器疯狂反复通断**（"啪嗒"响，电器乱跳） | 继电器断开断电 → LED 变红 | 设备损坏/火灾隐患 |
| 🌡️ 温湿度传感器 | 上报真实温湿度（25℃/50%） | **上报假数据**（温度飙到 99℃、湿度 100%） | 停止假数据 → 恢复真实值 → LED 变红 | 数据被篡改 |
| 🔊 智能音箱 | 播放正常语音 | **发出诡异噪音/怪声** | 静音 → LED 变红 | 骚扰/恐慌 |

### 8.2 分级阻断反应（映射 L1/L2/L3）

阻断不是"一刀切"，按风险等级分级响应：

| 风险等级 | 风险色 | 检测结果 | 阻断动作 | 语音播报 |
|---------|--------|---------|---------|---------|
| 0 正常 | 🟢绿 | 设备正常 | 无 | — |
| 1 侦察 | 🟡黄 | 设备在扫描 | 只记录观察，不阻断 | "发现可疑扫描，正在观察" |
| 2 拒绝服务 | 🟠橙 | 设备在洪水攻击 | 网络限流/告警 | "检测到洪水攻击，已限流" |
| 3 僵尸网络 | 🔴红 | 设备已被感染 | 完全隔离（网络阻断 + 物理断电） | "检测到僵尸网络感染，正在隔离" |

> **关键叙事**：只有僵尸网络（红）才执行"物理断电"这种最严厉的阻断，因为设备已被控制，必须彻底隔离。

### 8.3 阻断的技术实现（两级阻断）

**① 网络隔离（Pi 用 iptables）**：

```bash
# 检测到 192.168.4.11 被感染 → 网络层阻断
iptables -A FORWARD -s 192.168.4.11 -j DROP   # 阻断出站
iptables -A FORWARD -d 192.168.4.11 -j DROP   # 阻断入站
```

**② 物理阻断（Pi 通过 MQTT 发指令）**：

```python
# Pi 检测到感染后，发 MQTT 指令让设备自己执行物理阻断
mqtt.publish("community/door/control", "LOCK")     # 门禁锁死
mqtt.publish("community/plug/control", "OFF")      # 插座断电
mqtt.publish("community/camera/control", "STOP")   # 摄像头停止
mqtt.publish("community/speaker/control", "MUTE")  # 音箱静音
```

两级阻断结合 = 网络层（iptables 断网）+ 物理层（设备自己断电/锁死），双重保险，演示效果最震撼。

### 8.4 每个设备的阻断动作汇总

| 设备 | 物理阻断动作 | 执行器 | 网络阻断 |
|------|-------------|--------|---------|
| 摄像头 | 云台停 + 断电 | SG90 停止 | iptables |
| 门禁 | 舵机锁死 | SG90 锁死 | iptables |
| 路灯 | 灯熄灭/稳定 | LED 关闭 | iptables |
| 插座 | 继电器断开 | 继电器断电 | iptables |
| 传感器 | 恢复真实数据 | 软件恢复 | iptables |
| 音箱 | 静音 | 音频关闭 | iptables |

### 8.5 完整的检测-阻断时间线（秒级）

```
t=0s   攻击脚本启动，门禁（.4.11）开始发 Mirai 洪水
t=1s   门禁舵机"开门"（被入侵的物理表现）
t=2s   Pi 抓包 → 建设备图 → GNN 推理
t=3s   GNN 判定：门禁风险=红色（僵尸网络）
t=4s   语音播报："⚠️ 检测到 2 号设备——智能门禁，被僵尸网络感染，正在隔离"
t=5s   网络隔离（iptables 断门禁的网）
t=6s   物理阻断（MQTT 指令 → 门禁舵机锁死）
t=7s   门禁 LED 变红，舵机停止，大屏显示"门禁已隔离"
t=8s   处置日志记录，APP/电脑同步弹出告警
```

**全程 8 秒完成"检测→定位→语音→隔离→记录"**，节奏紧凑，观众能完整看到闭环。

## 10. 流量来源

**正常流量是"真的"，攻击流量是"模拟的"。**

| 流量类型 | 来源 | 真实性 |
|---------|------|--------|
| 正常流量 | ESP32 设备真实运行 MQTT/HTTP 协议（传感器真的上报温湿度、门禁真的上报开关状态） | ✅ 100% 真实 |
| 攻击流量 | 在一台设备（或 Pi）上跑攻击脚本，模拟 Mirai 的 UDP/GRE 洪水模式 | ⚠️ 模拟（但包是真实发出的） |

**为什么攻击流量用模拟的**：跑真 Mirai 恶意软件违法。但"模拟 Mirai 攻击模式"完全合法——用 scapy 几十行代码向自己的网络高频发送 UDP 洪水包（Mirai greip_flood = GRE 封装的 UDP 洪水、udpplain = 普通 UDP 洪水）。这些攻击包的特征（包长、协议、端口、速率）与数据集里的 Mirai 一致，Pi 能正确识别。

答辩诚实表述："正常流量来自设备真实运行，攻击流量用合法脚本模拟 Mirai 洪水模式（真实恶意软件不合法）。"

## 13. 能落地的分层路线

**别贪多，P0 跑通就赢，P1/P2 按时间加：**

```
P0 核心闭环（必须，先做）：
   ESP32 真实 MQTT + 脚本模拟 Mirai
   → Pi 抓包 → 设备图 GNN → 前端显示风险分级
   【跑通 = 项目成功，答辩有东西】

P1 震撼演示（有时间就加）：
   + 设备针对性反应（舵机/继电器/LED）
   + Pi 机器人（屏 + 语音 + 外壳）
   + WebSocket 三端联动
   【跑通 = 演示炸场】

P2 创新加分（可选）：
   + 蜜罐诱捕真实扫描（需外网）
   + APP 推送通知
   【跑通 = 答辩亮点】
```

每层都能独立演示、独立交付，不会因某个环节卡住导致整体失败。

## 14. 蜜罐取舍

- **核心演示（模拟攻击 → GNN 检测 → 隔离）不需要蜜罐**。
- 蜜罐提供的是**另一种能力**：主动诱捕真实攻击（而非被动检测）。若演示网络能连外网，开一个假 Telnet/SSH 服务，可诱捕互联网上真实的僵尸网络扫描（大量 Mirai 变种在扫 23 端口），这是**真实攻击数据**。
- **结论**：蜜罐降级为"可选加分项"（P2），不放在核心路径上，避免拖累进度。

## 16. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 现场 WiFi 不稳定 | 抓包丢包 | Pi 开热点，设备直连，不依赖外部网络 |
| 模型域偏移（数据集 vs 现场） | 误判 | 节点特征用 IP 无关的流量统计；必要时用回放数据集流量校准 |
| 真实 Mirai 不可用 | — | 合法脚本模拟 Mirai 洪水模式 |
| 良性流量稀缺 | 训练不平衡 | 时间切片 + 类别权重 / Focal Loss |
| 硬件故障 | 演示中断 | 每块 ESP32 独立，坏一块不影响整体；关键器件备份 |
