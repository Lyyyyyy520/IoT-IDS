# Mobile scoped device details

The Expo APP uses read-only mobile APIs for devices currently authorized to the
authenticated mobile user. It reuses existing observation, peer aggregation,
incident, and scope tables; these endpoints add no migration and do not change
administrator device or traffic APIs. The GNN, per-device baselines, and mobile
camera media capabilities remain unavailable; no score or detection result is
generated by the client.

## Endpoints

Both endpoints require the existing Mobile Bearer session. A Web cookie is not
an alternative credential. Requests are evaluated against the user's current,
non-revoked device and area scopes every time; the response is not a durable
authorization grant.

- `GET /api/v3/mobile/devices/{device_id}` returns a minimized device profile,
  connection/operation status, a bounded summary of currently published
  notices for affected devices, and capability availability. It deliberately
  excludes MAC, IP, peer addresses, ports, model evidence, and administrator
  incident fields.
- `GET /api/v3/mobile/devices/{device_id}/traffic?window=15m|1h|24h` returns
  minute aggregates downsampled to the requested fixed window, a short-lived
  in-process rate snapshot, coarse protocol categories, freshness, and a
  data-quality note. It does not return peers, IP addresses, raw protocols, or
  packet payloads. The API does not accept arbitrary time bounds or resolution
  parameters.
- `GET /api/v3/mobile/devices/{device_id}/history?window=1h|24h|7d` returns
  scalar telemetry from `v3_device_state_observations` and retained
  `device.connection_changed` events. The API checks current user scope,
  omits address/credential fields, selects actual observations into bounded
  time buckets, and marks truncation. Connection changes are not continuous and
  follow the existing event retention policy.
- `GET /api/v3/mobile/topology?window=1h|24h|7d` returns authorized profile
  nodes and only actual TX relationships from
  `v3_device_traffic_peer_minutes` where both endpoint devices are currently
  in the user's scope. It omits peer IPs and internal alert titles. Alert
  markers use only active, mobile-published, user-visible affected incidents.
- `GET /api/v3/mobile/notices/{incident_id}/replay?from=&to=` first verifies a
  currently visible mobile notice, then projects its public progress and only
  currently authorized affected devices from the retained incident replay.
  Device edges are returned only if both ends are in that visible set. Actor
  identity, administrator details, suspected-source links, and camera media are
  omitted.

An unknown device and a device outside the caller's current scope use the same
not-found response to avoid confirming that an inaccessible device exists.
Revoked scopes and area changes take effect on the next request. Retired devices
remain readable if still in scope and are marked as historical; their traffic
history is not deleted.

## Availability and freshness

Device connection status and operation mode are independent. `unknown` is never
presented as online. Traffic distinguishes:

- `no_samples`: no persisted sample is available; totals/rates are not invented;
- `warming_up`: the process-local short-term rate window has not accumulated
  enough observations;
- available data with a fresh or stale freshness indicator;
- unavailable service, reported as a structured service error.

Only actual aggregate rows can produce historical totals, including a real zero
counter. Gaps between returned time buckets are omitted rather than filled with
zero. The short-term window is bounded, process-local, and starts empty after a
backend restart; it is a display cache, not the historical source of truth.
Multiple backend processes do not share this rate window, so deployments should
route a user's requests consistently or accept that the live-rate capability may
be warming up on a worker. Persisted minute aggregates remain the historical
source of truth.

Traffic data is read-only and does not alter device identity, connection state,
operation mode, or security conclusions. Maintenance and disabled devices may
still have real traffic history. No traffic result implies that a device is
safe or under attack.

## Mobile presentation and privacy

The APP may show the user's own device name/type/area, coarse status, latest
safe scalar telemetry, observed relationships between two devices both inside
the user's scope, aggregate traffic, and broad protocol categories. It must not
call administrator device or peer endpoints as a fallback. It must not display
MAC/IP/ports, out-of-scope peers, graph identifiers, GNN scores/features, or
internal incident evidence. The camera firmware currently reports MQTT
heartbeat/device telemetry only; the repository has no video or snapshot API,
so the APP reports “not configured / no image” instead of loading a placeholder.

The device and traffic screens reuse the existing Mobile Bearer client and token
coordinator. Detail, history, and traffic requests are abortable and scoped to
the active device. A scope-related not-found result clears local detail,
refreshes the overview, and returns to the authorized list. In-memory data may
be retained after a transient network failure only with an explicit stale/offline
indicator; it is not persisted to AsyncStorage. Device list search and type,
connection, and active-notice filters are shared by list and topology views.
The notice list filters by occurrence time, device, severity, and status; mobile
acknowledgement remains a per-user “read/known” action and cannot resolve an
administrator incident. The APP has no report export/share action.

These screens contain household device information. This milestone does not
force screenshot prevention; deployments should use normal device lock and
screen privacy controls where needed. Polling runs only while the detail route
or topology view is focused and the APP is foregrounded (30 seconds for
profile/history/topology and 8 seconds for the simplified traffic view).
Returning to foreground starts fresh requests; leaving a route aborts pending
reads.

The current traffic view is intentionally a compact summary, not a full flow
forensics interface. It shows only actual saved rate/protocol data; mobile port
details, device baselines, and model conclusions are not available.
