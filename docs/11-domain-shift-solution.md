## 1. 背景与问题诊断

### 1.1 现象

P0 联调时，检测管道（抓包 → 建设备图 → GNN 推理 → 返回）已跑通，但 **8 台设备全部被判为"拒绝服务(橙)"**，触发攻击后也无设备变红——模型完全无法区分正常与攻击。

### 1.2 三大根因（定量）

#### 根因一：时间窗口不匹配（60 倍）

| | 训练 | 检测 |
|---|------|------|
| 窗口大小 | `window_size=3600` 秒（1 小时） | `window_seconds=60` 秒（1 分钟） |

检测时 `flow_count`、`total_packets` 等特征天然只有训练时的 **1/60**。模型看到的是"缩小 60 倍的特征"，必然全判错。

#### 根因二：特征画像不匹配（单目标 vs 多目标）

模型训练于 CICIoT2023，其 benign 类画像（反 log1p 后的原始量级）与我们的模拟对比：

| 特征 | benign(正常) | DoS(拒绝服务) | 我们的模拟 |
|------|-------------|--------------|-----------|
| unique_dst_ports | **14.8** | 2.5 | 1（只连 1883） |
| unique_dst_ips | **8.6** | 2.1 | 1（只连 Pi） |
| internal_ratio | 0.2 | 0.5 | 1.0（全内网） |
| unique_protocols | 2.1 | 1.2 | 1（纯 TCP） |

我们的"纯 MQTT 单目标"流量，特征上最接近 **DoS 类**而非 benign 类——这就是全判橙的直接原因。

#### 根因三：设备规模不匹配（6 vs 105）

| 场景 | 设备数 |
|------|--------|
| 真实智慧社区 | 几十~几百台 |
| Gotham 测试床 | 78 台 |
| CICIoT2023（训练集） | 105 台（或 43） |
| **我们** | **6 台** |

6 台设备全部只连 Pi，图退化成"星型拓扑"，而训练图 ~100 节点。GNN 的图注意力在 6 节点退化图上几乎没有图结构可学，且"在众多设备中找异常"的核心难点被抽掉了。

## 2. 核心原理

### 2.1 "网络一致"的精确定义

IDS 不看原始数据包，而是把每台设备在一段时间窗口内的流量**聚合压缩成 13 个特征**：

```
flow_count, total_packets, total_bytes, avg_packets, avg_bytes,
max_packets, unique_dst_ports, unique_dst_ips, unique_src_ports,
unique_protocols, tcp_flags_mean, avg_flow_duration, internal_ratio
```

（先 `log1p` 变换，再标准化。）

因此"网络一致"的定义是：

> **让模拟设备的 13 维特征，落在训练集 benign（正常）/ botnet（攻击）类的特征分布内。** 不是逐包一致——逐包一致既不可能也没必要。

### 2.2 IDS 只认特征，不认物理功能

舵机转没转、灯亮没亮，IDS 看不见；它只"看"网线上的包（IP、端口、协议、速率、方向）。所以物理功能只是答辩演示的视觉效果，与检测正确性无关。真实设备与模拟设备只要**网络行为一致**，IDS 就分不出、也无需分出区别。

### 2.3 域偏移是学界公认的头号难题

- 跨数据集测试：F1 掉 **0.20~0.27**，误报率高达 **30%**
- "同数据集评估会系统性高估真实部署性能"
- 主流解法：**迁移学习/微调**（SSCL-IDS 证明 <20 条样本微调即 AUROC>80%）、**数字孪生**（Gotham/IDS-Twin 多协议真实流量）、**自监督学习**、**鲁棒模型**（树模型比深度学习抗偏移 6~23%）

### 2.4 生产系统的做法（为什么它们没这个问题）

生产 NDR（Darktrace/Vectra/ExtraHop/Corelight）用**多层检测引擎**：

| 层 | 作用 | 有无域偏移 |
|----|------|-----------|
| 签名（Suricata 规则） | 查已知攻击（Mirai 签名） | 无（规则匹配） |
| 基线/行为异常（核心） | 学**本网络自己**的正常流量，标偏离 | 无"公共数据集偏移"（学的是本地） |
| ML 模型 | 有监督 + 无监督 | 有（配合基线用） |
| 威胁情报 + 加密流量分析 | IOC 情报 + JA3/JA4 指纹 | 无 |

**核心心法**：不拿"别人的数据集"当"你的网络"，学"你自己网络"的基线。

商业图 NDR（Darktrace/Vectra）的图建模（节点=主机、边=通信、权重=频率/流量）**与我们设备图 GNN 同源**——区别只在：商业用**无监督基线**（抗偏移），我们用**有监督分类**（易偏移）。

## 3. 数据集定位

### 3.1 CICIoT2023 是对的选择

对"智慧社区 IoT 僵尸网络检测"这个具体场景，CICIoT2023 是目前**最契合**的公开数据集：

| 评估维度 | CICIoT2023 | 说明 |
|---------|-----------|------|
| 场景契合 | ✅ 智能家居（非企业网） | 最接近"智慧社区" |
| 目标攻击 | ✅ 含 Mirai | 正是要检测的僵尸网络 |
| 设备规模 | ✅ 105 台（样本 117 个内网 IP） | 有"社区"体量感 |
| 时效性 | ✅ 2023 年 | 比老数据集新 |
| 标签丰富 | ✅ 7 大类 33 种攻击 | 覆盖侦察/DoS/DDoS/Mirai |

对比其他候选数据集：

| 数据集 | 为什么不契合 |
|--------|-------------|
| BoT-IoT（2018） | 正常流量合成、仅 ~5%，类别极度不平衡 |
| N-BaIoT（2019） | 仅 9 台设备，规模太小，偏老 |
| IoT-23（2020） | 偏"恶意软件样本"，非"设备行为" |
| TON_IoT（2019） | 偏工业物联网（IIoT），非智能家居 |

### 3.2 三大局限（诚实面对）

1. **域偏移**（最关键）：这是**所有公开数据集共有的**，非 CICIoT2023 独有。文献明确"domain shift 甚至在同一数据集内部都严重"。
2. **样本无设备类型字段**：导致"设备类型异构"不可行（只能用协议+角色异构），但影响有限（IDS 靠"行为变化"而非"设备品牌"）。
3. **样本是抽样子集**：`flows_sample.csv` 可能丢失部分设备/攻击的多样性。

### 3.3 关键结论：数据集是次要矛盾

> **无论选哪个公开数据集，部署到"我们的模拟/真实流量"都会有域偏移。所以"换更好的数据集"解决不了根本问题，"怎么缓解域偏移"才是关键。**

因此 CICIoT2023 的定位是：**预训练集，而非最终训练集**。

```
① CICIoT2023（丰富、多样、有 Mirai）
   ↓ 预训练 HTGAT，学到"通用 IoT 流量 + 攻击"的表征
② 我们自己的模拟社区流量（少量、贴合场景）
   ↓ 微调，让模型贴合我们的设备/协议/网络
③ 真实社区流量（将来）
   ↓ 再微调或重新学基线
```

这是 SSCL-IDS 验证过的"预训练 + <20 条样本微调即 AUROC>80%"路线，也是生产系统"预训练 + 本地适配"的逻辑。

## 4. 模型升级方案（异构时序图注意力网络）

### 4.1 前沿趋势（2024-2025）

针对智能家居/智慧社区的图入侵检测，学界已转向"异构图 + 时序 + 边特征"：

| 工作 | 核心思想 | 借鉴点 |
|------|---------|--------|
| SeIoT（IEEE TIFS 2024） | 异构图注意力建模设备-环境交互 | 异构节点+边 |
| FIR-GNN（IEEE TCE 2025） | 流交互关系 GNN，嵌入网关 | 通信关系即边 |
| StrucTemp-GNN | 动态异构图 GNN | 图要"动态+异构" |
| NID-TGN（2025） | 时序图网络捕捉时空关系 | 时序建模 |
| APS-T（IEEE TII 2024） | 从 MQTT 包头构建图 + 时空注意力 | 协议级构图 |
| E-GraphSAGE/EGNN（2025） | 边特征显著提升（F1 达 1.0） | 边不能是 0/1 |

### 4.2 当前 GAT 的四个缺口

| 缺口 | 现状 | 问题 |
|------|------|------|
| 1. 同构假设 | 所有设备当同类节点 | 摄像头和传感器网络行为本质不同，被抹平 |
| 2. 二值边 | 通信=1，否则 0 | 忽略通信频率/字节/协议，丢失关键边信息 |
| 3. 时序建模粗糙 | 用"时序边"硬连相邻窗口 | 权宜之计，非真时序建模 |
| 4. 纯有监督分类 | 4 类分类，训练于 CICIoT2023 | 最易受域偏移影响 |

### 4.3 可行性结论（已查数据字段）

| 需要的异构 | CICIoT2023 样本有吗 | 结论 |
|-----------|---------------------|------|
| 边类型（协议） | 无应用协议列，但端口可推断 | ✅ 可行（1883→MQTT、53→DNS、80/443→HTTP、123→NTP、5353→mDNS） |
| 节点角色（设备/网关/外网） | 有内网 117 IP + 外网 IP | ✅ 可行（192.168.137.1=网关，其余内网=设备） |
| 设备类型（摄像头/传感器） | 无此字段 | ❌ 不可行（但影响有限） |

### 4.4 具体架构（HTGAT）

**图构建（协议异构 + 角色异构）：**

```
节点（3 种类型）：gateway / device / external
边（6 种类型，从 dst_port 推断）：
  MQTT(1883/8883)、HTTP(80/443)、DNS(53)、NTP(123)、mDNS(5353/1900)、other
边特征（带权重，非 0/1）：flow_count、bytes、duration
```

**模型架构（PyTorch Geometric 现成组件）：**

| 层 | 组件 | 作用 |
|----|------|------|
| 输入编码 | 每类节点 type embedding + 每条边协议 embedding + 边特征 MLP | 区分异构 |
| 消息传递 | HGT（Heterogeneous Graph Transformer）或 HAN metapath attention | 类型特定注意力 |
| 时序建模 | 保留"时序边" + 可选 TGN 记忆单元 | 捕捉行为随时间变化 |
| 输出 | 节点分类头 → 4 级风险 | 保持现有目标 |

### 4.5 实施路径（两步，务实）

1. **第一步（低成本验证）**：不改模型，先只做"边特征化"——把二值邻接矩阵换成"带协议类型 + 通信权重的边特征"，看检测是否提升。
2. **第二步（正式升级）**：确认边特征有效后，升级为完整 HGT。

## 5. 设计原则（五条铁律）

### 5.1 保真度
模拟必须**对齐真实 IoT 的 13 维特征分布**，而非随意拍脑袋设模式。低保真模拟放真实场景必然失效。

### 5.2 随机化（防死记硬背）
所有参数（间隔、端口、包大小、目标）带**随机扰动**。若模拟是确定性的，模型只会背"包去 1883=正常、包去 80=攻击"，这不是入侵检测。加方差后，模型被迫学普遍规律（低频/低量/内网=正常，高频/多目标/外网=攻击）。

### 5.3 训练测试分离（防开卷考试）
训练和测试用**不同的随机种子、设备组合、甚至设备类型**。同生成器产出训练+测试 = 生成器过拟合 = 自欺欺人。

### 5.4 真实数据验证（最终判据）
模拟得分再高，最终必须**拿真实 IoT 流量验一次**（哪怕几条），否则无法证明可迁移。

### 5.5 规模
社区级设备数（**20~40 台**），而非家庭级（6 台）。设备数决定图的拓扑与 GNN 尺度。

## 6. 架构方案

### 6.1 混合物理 + 虚拟（推荐）

```
物理层（6 块 ESP32，真实硬件）
  ├─ 门禁(舵机)、路灯(LED)、插座、传感器、音箱、摄像头
  └─ 作用：真实硬件视觉效果 + 少量真实流量

虚拟层（Pi 上的社区流量生成器，20~40 台虚拟设备）
  ├─ 各自独立 IP（如 192.168.4.100~199）
  ├─ 每台模拟不同设备类型 + 多协议真实流量
  └─ 作用：撑起"社区规模"，让设备图有 20~40 节点

IDS（后端）
  └─ 同时看物理+虚拟的全部流量，在"社区规模"图上检测
```

这是 Gotham/IDS-Twin 的"物理 + 仿真混合"标准做法，同时解决：图拓扑退化、GNN 尺度匹配、演示观感、成本。

### 6.2 多协议（对齐真实 IoT）

正常流量不应只有 MQTT，而应覆盖真实设备的协议组合：

| 协议 | 端口 | 频率 | 作用 |
|------|------|------|------|
| MQTT | TCP 1883 | 5~15s 随机 | 主业务遥测 |
| DNS | UDP 53 | 30~60s 随机 | 域名解析 |
| NTP | UDP 123 | 60~120s 随机 | 时间同步 |
| HTTP | TCP 80/443 | 60~180s 随机 | 云 API 心跳 |
| CoAP | UDP 5683 | 60~180s 随机 | 约束设备通信 |

### 6.3 特征对齐目标（定量）

**正常设备 → 对齐 benign 画像：**

| 目标特征 | benign 值 | 设计方向 |
|---------|-----------|---------|
| unique_dst_ports | ~15 | 多端口（1883/53/123/80/443/5683） |
| unique_dst_ips | ~8-9 | 多目的（Pi 内网 + 公网云/DNS/NTP） |
| unique_protocols | ~2 | TCP + UDP |
| internal_ratio | ~0.2 | 大部分外网，少量内网 |
| avg_flow_duration | ~116s | 持久连接（MQTT 长连接） |

**攻击设备 → 对齐 botnet 画像：**

| 目标特征 | botnet 值 | 设计方向 |
|---------|-----------|---------|
| total_packets | ~28,359 | 高频发包（洪水） |
| avg_packets | ~3,126 | 单流海量包（是 benign 的 60 倍） |
| unique_dst_ips | ~9 | 扫描多个随机 IP（不是只打 1 个） |
| unique_dst_ports | ~14 | 扫描多端口（23/2323/80 等） |

## 7. 分阶段实施计划

### 阶段 0：修复时间窗口（最根本）

- 用 `window_size=60`（或 120~300）重新建图 + 重训，使训练=检测窗口
- 验证：正常设备从"橙"变"绿"

### 阶段 1：正常行为真实化（多协议）

- 改 `community_device.ino` 正常行为：加 DNS/NTP/HTTP/CoAP，降 MQTT 频率，全部带随机抖动
- 验证：抓包能看到 5 种协议、多端口多 IP，特征落在 benign 分布内

### 阶段 2：攻击行为真实化（Mirai 四阶段）

- 改 `doAttack()`：端口扫描（随机 IP 的 23/2323）+ 暴力破解（Telnet 尝试）+ C2 通信（持久 TCP）+ DDoS（UDP 洪水 512~1400 字节）
- 验证：攻击设备 `unique_dst_ips` 明显大于正常设备，检测变"红"

### 阶段 3：社区规模（虚拟设备）

- Pi 上写"社区流量生成器"，生成 20~40 台虚拟设备（独立 IP、独立参数、随机扰动、多设备类型）
- 验证：设备图有 20~40 节点，非星型拓扑

### 阶段 4：模型升级（边特征化 → HGT）

- 4a. 边特征化：二值边 → 协议类型 + 通信权重（低成本验证）
- 4b. 完整 HGT：异构图注意力 + 时序 + 4 级分类（对齐 SeIoT/FIR-GNN）
- 验证：边特征化后检测是否提升；HGT 后契合异构场景

### 阶段 5：微调 + 跨域验证

- 采集现场流量（正常+攻击各几十条），在 CICIoT2023 预训练模型上**微调**（而非重训），重新导出 ONNX
- 验证：正常绿、攻击红稳定；并尽量用真实 IoT 流量做一次最终验证

## 8. 验证标准（完成判据）

| 阶段 | 完成判据 |
|------|---------|
| 0 | 训练窗口 = 检测窗口，正常设备不再全判橙 |
| 1 | 抓包可见 MQTT/DNS/NTP/HTTP/CoAP 多协议，特征对齐 benign 画像 |
| 2 | 攻击设备 unique_dst_ips 明显 > 正常设备，检测变红 |
| 3 | 设备图 20~40 节点，非星型拓扑 |
| 4 | 边特征化后检测提升；HGT 契合异构场景 |
| 5 | **正常设备稳定绿、攻击设备稳定红**（P0 闭环通），并通过真实流量验证 |
